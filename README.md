# NAWI Compliance & Test Report Automation System

Smart India Hackathon 2026 · Problem Statement 26035 · Legal Metrology / Measurement Standards

A local-first prototype for registering Non-Automatic Weighing Instruments, recording laboratory test conditions and observations, tracing rule-based evaluation outputs, routing sessions for review, and generating report files. This is a prototype and does not provide official legal certification.

## Technology

- Frontend: React 18, Vite, Lucide React, responsive custom CSS
- Backend: Python 3.11+, FastAPI, Pydantic Settings, SQLAlchemy 2
- Local database: SQLite by default; database URL is configurable for PostgreSQL deployment
- Authentication: JWT bearer tokens and PBKDF2 password hashes
- Reporting: ReportLab PDF and python-docx DOCX

## Run locally

Use two terminals from `nawi-compliance-system`.

### Backend (PowerShell)

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
uvicorn app.main:app --reload
```

The API is at `http://localhost:8000`; interactive API documentation is at `http://localhost:8000/docs`. SQLite initializes on first start. Demo accounts are seeded automatically.

### Frontend (PowerShell)

```powershell
cd frontend
$env:NODE_OPTIONS='--use-system-ca'
npm.cmd install --cache .npm-cache
npm.cmd run dev
```

Open `http://localhost:5173`. Set `VITE_API_URL` in a frontend `.env` file if the API is hosted somewhere other than `http://localhost:8000`.

## Data model

SQLAlchemy entities: User, Instrument, TestSession, TestObservation, ComplianceResult, RuleConfiguration, Report, Attachment, AuditLog. The SQLAlchemy models use portable types and foreign keys; configure `DATABASE_URL` to a PostgreSQL SQLAlchemy URL to use PostgreSQL. Local SQLite database file defaults to `backend/nawi.db`.

## Compliance rule safety

The modules for weighing/MPE, repeatability, eccentricity, tare, validation, and aggregation keep calculations separate. On a brand-new database only, startup seeds a clearly marked synthetic demo profile so the compare/report workflow can be tried immediately. It does not add demo values if any OIML R-76 rules already exist, and never replaces configured editions. Administrators can configure rule records from **Rule configuration**; each record stores standard, edition, rule code, test type, accuracy class, applicable load range, limit, unit, comparator, description, source reference, active state and timestamps. Creating a rule for a new edition deactivates the previous edition. Rule writes and evaluation events are recorded in the audit log.

For a controlled UI/API demonstration only, an administrator can use **Load demo profile** on the Rule Configuration page; a brand-new database receives the same profile during startup. The five illustrative class III rules (MPE 0.02 kg, weighing 0.02 kg, repeatability 0.02 kg, eccentricity 0.03 kg, tare 0.01 kg) apply from 0 to 26 kg. These numbers are synthetic prototype thresholds, not official OIML R-76 limits, do not establish legal compliance, and are restricted to demonstration. The manual action refuses to proceed while a different active OIML R-76 edition exists. Compliance status shows the active configurations and clearly labels this profile non-official. For real measurements, an administrator must enter the applicable controlled values and source references before evaluating.

When no active rule matches a test type, class and observation range, or when observations are insufficient, that test result is `NOT_EVALUATED` with a reason (the API uses `MISSING_RULE` when no matching rule is available). Safe raw values remain visible. An overall result is `NOT_EVALUATED` if any of the five mandatory tests is unevaluated; the dashboard keeps it separate from PASS and FAIL. Submission and officer approval revalidate against the current active rule records and require all five evaluations to pass. A rule comparison may use the instrument capacity unit, `e`, or `d`; mass conversions use exact SI scale factors. Unsupported units remain unevaluated. Only enter values checked against the applicable controlled standard and cite the specific source in the rule record. This prototype cannot verify the authority of an administrator-entered source citation. Both add and replace observation endpoints reject non-numeric, non-finite, or out-of-capacity applied loads before saving any rows.

### Demonstration walkthrough

1. Start backend and frontend using the commands above and sign in as `admin@nawi.local` / `Admin@123`.
2. On a fresh database, the clearly labeled demo profile is already active. Open **Rule Configuration** to confirm its five class III entries.
3. Register a class III instrument with 0–26 kg capacity, then create a test session.
4. Record weighing points across the capacity (for example 0.2, 5, 13, and 26 kg), at least two repeatability readings at one common load, position readings at one common load, and a tare observation. Values must use the instrument's capacity unit; applied loads must be within min/max capacity.
5. Run compliance from the session. The API returns an overall status and, per test, the rule metadata and limits used. PASS/FAIL here only reflects the synthetic configured profile. An absent/inapplicable rule or insufficient observation set stays NOT_EVALUATED; do not interpret that as PASS.
6. Generate a report from the session and inspect it in the report repository. Submission and officer approval require all five current evaluations to pass; the demo profile is for workflow demonstration, not instrument certification.

`Instrument n` is calculated server-side as maximum capacity divided by `e`. Metrological characteristics lock after a test session exists. A unit change before testing converts maximum/minimum capacity, `e`, and `d` using the standard mass-unit scale factors.

## Reporting and workflow

PDF uses ReportLab tables and page headers/footers; DOCX uses native document tables. Reports include instrument parameters, environmental conditions, observations, calculated results, limits/units, rule codes/editions and an explicit evaluation state. If rules are unavailable, they say evaluation could not be finalized and do not imply certification. A technician can save observations and run evaluation; only fully evaluated passing sessions can be submitted. Approving officers can approve or reject reviewable sessions, with a mandatory reason on rejection. Reports can be generated for a test with recorded evaluation results and downloaded from the repository.

## Known prototype limitations

- Edition-controlled MPE and test limits are intentionally not supplied. Admin-entered references are traceable, but a responsible metrology authority must verify every rule before operational use.
- Rule semantics provide safe generic comparisons for entered values; they do not themselves establish that an entered rule set fully captures every prescribed OIML test procedure or legal decision.
- Attachments are restricted to JPEG/PNG/WebP/PDF/DOCX, 10 MB maximum, and stored locally. Production malware scanning, retention controls and PostgreSQL schema migrations are not included.
- This is a local prototype, not a legal certification system or production-hardened deployment.

## Share a prototype with Netlify

Netlify can host the React/Vite frontend as a static site. It does not run this FastAPI backend. To make sign-in and saved data work for other people, first deploy the backend to a public Python API host and configure a persistent database; the default SQLite file and uploaded attachment folder are local files and are not suitable for an ephemeral host.

1. Push this repository to a Git provider and import it into Netlify. The root `netlify.toml` sets the frontend base directory, `npm run build`, the `dist` publish folder, and SPA routing.
2. Deploy the FastAPI backend separately. Configure `DATABASE_URL` for a persistent PostgreSQL database, set `JWT_SECRET` to a long random private value, and set `CORS_ORIGINS` to your exact Netlify site origin (for example, `https://your-site.netlify.app`). If you need uploaded evidence to persist, configure durable file storage; the current attachment implementation writes to local disk.
3. In Netlify site environment variables, set `VITE_API_URL` to the public backend origin (for example, `https://your-api.example.com`, with no `/api` suffix). Redeploy after setting it so Vite includes the API address in the frontend build.
4. Share the Netlify URL. The included demo accounts are public prototype credentials; do not put real personal or lab data in this demo.

For local development, copy `frontend/.env.example` to `frontend/.env`; its default API URL is `http://localhost:8000`. Never use the local demo JWT secret on a public backend.
